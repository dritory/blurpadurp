# Localization

The site chrome is bilingual: English (default, unprefixed) and
Norwegian bokmål (under `/no`). **The brief itself is not translated.**

That split is the whole design, so it's worth stating plainly before
anything else.

## What is and isn't translated

| Surface | Translated |
|---|---|
| Nav, footer, page furniture | yes |
| `/about`, `/privacy` prose | yes |
| Subscribe form, flash messages | yes |
| Preferences page (`/manage/:token`) | yes |
| Confirmation email, brief email wrapper | yes |
| Issue title and body | **no** — composer output, English |
| Category names | no — one `name` column, English |
| Atom feed, sitemap, robots.txt | n/a — one of each, site-wide |
| `/admin/*` | no, and deliberately: one operator |

A Norwegian page that can show a brief carries a one-line note saying
the brief is in English (`Strings.briefLanguageNote`, rendered by
`BriefLanguageNote`). Better the reader is told than discovers it.

## Where things live

- `src/shared/i18n.ts` — the locale list, path helpers, and the full
  string tables. One `Strings` interface, one object per locale, so a
  missing key is a **type error**. The long-form prose (`about`,
  `privacy`) is arrays of blocks; TypeScript can't see a dropped
  section there, so `i18n.test.ts` compares the block structure across
  locales instead.
- `src/views/*` — every public view takes an optional `locale` and
  defaults to English, so a caller that hasn't been updated renders
  exactly what it rendered before.
- `src/api/public.tsx` — reader routes are registered in a loop, once
  per locale, each handler closing over its own locale.
- `src/api/subscription.tsx` — `POST /subscribe` likewise; the
  signed-token routes read the language off the subscriber's row.

## URL shape

English is unprefixed and Norwegian lives at `/no`. Every pre-existing
URL, inbound link, archive permalink and R2 key therefore stays exactly
where it was — adding a language must not invalidate the archive.

`localizePath(locale, path)` is the only way to build a localized link;
`splitLocale(pathname)` is the only way to read one. The Norwegian root
is `/no`, with no trailing slash, so there is exactly one URL per page.

## Locale is never negotiated from `Accept-Language`

Reader pages are served from a shared edge cache (Cloudflare in front of
R2) keyed on **path alone**. Varying the response body by a request
header behind that cache hands the wrong language to whoever asks
second. The prefix in the URL is the entire mechanism. Do not add
content negotiation without first making the cache key include the
header — and note that doing so doubles the edge working set.

A redirect on `/` based on `Accept-Language` would be equally wrong for
the same reason: the redirect itself would be cached.

## Caching

- `page-cache.ts` (the origin's R2 cache) keys on `pageCacheKey(locale,
  key)`. The default locale keeps its bare key, so existing cache
  objects survived the deploy. **Locale must be in the key** — these
  bodies differ by language and nothing else.
- `static-export.tsx` writes `localeKey(locale, key)`: bare for the
  default locale, `no/<key>` otherwise. The Worker's `pageTarget()`
  mirrors it. `static-export.test.ts` pins the prefix list on both
  sides; the per-page mapping is still convention, so read both when
  changing either.
- Publish-time purge covers each locale's rolling pages.

## The subscriber's language

`email_subscription.locale` (mig 076), because once a reader is in their
inbox there is no URL to recover it from. The subscribe form posts a
hidden `locale`; it's validated against the known set on the way in, not
trusted, since it lands in a `CHECK`-constrained column.

Re-submitting the subscribe form for an already-confirmed address does
**not** change the stored language — that's what the preferences page is
for, and a stray form post shouldn't silently re-language someone's mail.

## Adding a locale

1. Add it to `LOCALES` and fill in `LOCALE_PREFIX`, `HTML_LANG`,
   `DATE_LOCALE`, `LOCALE_NAME`.
2. Add the `Strings` object. TypeScript will list everything missing.
3. Add the prefix to `LOCALE_PREFIXES` in `infra/worker/src/index.ts`
   and deploy the Worker. The drift guard fails the build until you do.
4. Widen the `email_subscription.locale` CHECK constraint.
5. Re-run a publish so the static export writes the new keys.

Steps 3 and 5 are the ones that bite: without them the new locale's
pages exist on the origin and are invisible at the edge.

## If the brief ever needs translating

The honest options, in rough order of cost:

1. **A second composer pass** against an `nb-NO` prompt, from the same
   `ComposerInput`. Roughly doubles composer cost per issue, and needs
   its own prompt version, gold examples, and gloss handling — the voice
   rules in `docs/composer-prompt.md` are written in and for English.
2. **Machine translation of the composed HTML**, which is cheap and
   which the editorial standard in `docs/concept.md` should probably
   reject: the register (wry, dry, understated) is exactly what survives
   translation worst.
3. **A Norwegian editorial line**, i.e. a different brief, not a
   translation of this one.

Whichever, it needs a second `composed_html` per issue and a decision
about what the archive does with issues that predate it. That's why the
current split stops at the chrome.
